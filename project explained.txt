REEL ROOM - THEATRE BOOKING
PROJECT, JAVA CODE, DATABASE, AND SYSTEM GUIDE

1. PROJECT SUMMARY

Reel Room is a Java theatre-seat booking website. A visitor first sees a minimal sign-in or account-creation page. After signing in, they can choose one of three films, choose an available seat, and save the booking to MySQL.

The Java server serves both the website and its API. MySQL stores accounts, sessions, and reservations. Because seat availability is read from the shared theatre_bookings table instead of being kept only in browser memory, all accounts see the same booked seats. Bookings remain after the Java server restarts.

2. BASIC TECH STACK

Backend: Java 11 or newer, using the built-in JDK HTTP server.
Build and launch: Maven, Maven Wrapper, and run.sh.
Database: MySQL, accessed with JDBC and MySQL Connector/J.
Frontend: plain HTML, CSS, and browser JavaScript in index.html.
Web fonts: DM Sans, DM Mono, and Fraunces, loaded from Google Fonts.
Server port: 8080.
Database: booking_app. Theatre tables use the theatre_ prefix.

There is no Spring, React, ORM, separate Node server, or external authentication service in this project. The Java server is the backend and the frontend is a static HTML page served by that same server.

Build versions: Maven Wrapper 3.3.2 downloads Maven 3.9.9. pom.xml uses Maven Compiler Plugin 3.13.0 and Exec Maven Plugin 3.5.0. The compiler targets Java 11 and enables jdk.httpserver.


3. JAVA PACKAGES AND LIBRARIES

There is no package declaration at the top of the Java source files. For this small project, its Java classes are in the default package. The import statements bring in the following JDK packages:

java.lang
Automatically imported by Java. It supplies common types used throughout the source, including String, Integer, and the base Exception classes.

com.sun.net.httpserver
HttpServer listens for browser requests. HttpExchange represents one request and its response. This is part of the JDK module jdk.httpserver, which Maven enables in pom.xml.

java.io
IOException represents file and network input/output errors.

java.net
InetSocketAddress binds the server to a port. URLDecoder decodes form values sent by the browser.

java.nio.charset and java.nio.file
StandardCharsets makes text encoding explicit. Files and Path read index.html from the project folder.

java.sql
Connection, DriverManager, PreparedStatement, ResultSet, SQLException, and Statement provide JDBC access to MySQL. Prepared statements pass values separately from SQL, which avoids treating user input as SQL code.

java.util
Map and HashMap store decoded form fields. Base64 encodes salts and tokens. Locale normalizes usernames.

java.util.concurrent
Executors creates the server's worker thread pool.

java.util.regex
Pattern checks username rules.

java.security and javax.crypto
SecureRandom generates password salts and session tokens. MessageDigest calculates SHA-256 hashes and compares password hashes safely. SecretKeyFactory implements PBKDF2; PBEKeySpec from javax.crypto.spec supplies its password, salt, iteration count, and output size.

java.time, java.time.temporal, and java.time.format
Instant and ChronoUnit set and check the seven-day session expiry. DateTimeFormatter formats the cookie expiry date, and ZoneOffset supplies UTC. Timestamp, from java.sql, writes the expiry to MySQL.

External Java library
MySQL Connector/J, declared in pom.xml as com.mysql:mysql-connector-j 9.2.0, implements the JDBC connection to MySQL. No Java JSON library is used; the small API responses are assembled as JSON strings in the Java code.

5. JAVA CODE WALKTHROUGH

MovieBooking.java - web server and request controller

MovieBooking has two static fields. bookingSystem is the in-memory catalogue and domain-object lookup. auth is configured with the fixed table names theatre_accounts and theatre_sessions and the cookie name theatre_session. Static fields let the HTTP request handler use the same service objects throughout the server lifetime.

main() is the startup sequence. First it opens MySQL and creates or updates the catalogue and booking tables through BookingSystem.initialize(). Then it creates the account and session tables through AccountAuth.initialize(). If database initialization throws SQLException, the server does not start. After initialization, HttpServer.create() binds to port 8080. Executors.newFixedThreadPool(8) allows up to eight request tasks to run at once. createContext("/", ...) registers one handler for the root page and API paths; handleRequest() distinguishes those paths. start() begins accepting requests.

handleRequest() is the router. It reads the URL path with getRequestURI().getPath() and checks the HTTP method. GET / reads index.html from the current project folder. POST /api/register and POST /api/login are public authentication actions. GET /api/session reports the current login. POST /api/logout removes it. For the other /api/ paths, the router calls auth.currentUser() first. Without a valid user it returns 401 and does not call the movie or booking logic. With a user it dispatches GET /api/movies, GET /api/seats, or POST /api/book. An unknown path returns 404. The outer SQLException handler returns 500 for database failures. Each response closes its HttpExchange in send().

authenticate() handles both account actions. The boolean register parameter selects register() or login(). The request body is decoded as UTF-8 and parsed by readForm(). On success, the method sets the session cookie and returns the username. Account creation returns 201 Created; a normal login returns 200 OK. AccountAuth.AuthException contains a status and a safe message for invalid input or an incorrect login, and authenticate() returns that status to the browser.

sendSession() calls auth.currentUser() using the request's Cookie header. It returns JSON with authenticated=false when there is no valid session, or authenticated=true and the normalized username when there is one. It lets index.html decide whether to leave the visitor on the landing screen or show booking.

sendMovies() uses the catalogue in BookingSystem, loops through the three Movie objects, and appends a JSON object for each one. available is calculated from MySQL at request time, so the result reflects bookings saved by any account. sendSeats() reads movieId from the query string, parses it, finds the Movie, and calls getSeatsJson(). An unknown movie returns 404.

bookSeat() parses movieId, seat, and name from a URL-encoded POST body. It rejects a missing movie, invalid seat label, or blank name with 400. The authenticated AccountAuth.User is supplied by the router, not accepted from the form, so a browser cannot choose another account ID. The account ID and submitted customer name are passed to Movie.bookSeat(). A successful insert returns 200; a database duplicate-key response becomes 409 because that seat is already taken.

getSeatNumber() maps the visible seat label to the database's zero-based index. It uppercases the first character to get a row from A through E, reads the number from 1 through 8, and calculates rowNumber * 8 + seatInRow. Thus A1 maps to 0, A8 to 7, B1 to 8, and E8 to 39. Any label outside those bounds maps to -1 and is rejected.

readNumber() returns an integer or -1 if parsing fails. readForm() creates a HashMap, splits a form body at ampersands, splits each pair only at its first equals sign, URL-decodes both sides as UTF-8, and stores the result by field name. sendJson() chooses the application/json content type. send() converts the response string to UTF-8 bytes, sets Content-Type and Cache-Control: no-store, writes the status and body, then closes the exchange. No JSON serializer is involved; responses are small strings built by the application.

BookingSystem

BookingSystem owns a Movie array containing After the Rain, The Last Ticket, and Orbit, Somewhere. Each has an ID, a display time, and 40 seats. The array is the catalogue the HTTP API loops through. MySQL stores a copy of the movie details so theatre_bookings can use a foreign key to theatre_movies.

initialize() uses JDBC statements for schema setup. CREATE TABLE IF NOT EXISTS creates theatre_movies and theatre_bookings only when missing. INSERT IGNORE with a PreparedStatement seeds each default movie without overwriting existing rows. The final ALTER TABLE tries to add account_id to a booking table created by an older version. MySQL error 1060 means that column already exists and is intentionally ignored; other SQL errors are rethrown so startup fails instead of silently hiding a schema problem.

getMovies() returns the configured array. getMovie(id) scans it and returns the matching Movie object or null. Movie's getId(), getTitle(), getTime(), and getTotalSeats() methods return its four fields to the API and initialization code. The app's movie list is defined in Java; booking and seat availability are read from MySQL.

Movie

Movie is the theatre domain object. Its private fields id, title, time, and totalSeats describe one screening. The constructor initializes those fields, and the getter methods expose the values needed by BookingSystem and the JSON response without exposing direct field mutation.

bookSeat(seatIndex, customerName, accountId) first checks that the index is in the 0-to-totalSeats-minus-one range. It then opens a JDBC connection and prepares an INSERT into theatre_bookings with movie ID, seat index, customer name, and the authenticated account ID. Each question mark is bound with setInt() or setString(). try-with-resources closes the statement and connection on success or failure. If MySQL reports error 1062, the composite primary key already exists and the method returns false. Other SQL failures are rethrown. synchronized serializes calls on this Movie object in one JVM; MySQL's primary key also protects the seat if different worker threads or separate server instances race.

getAvailableSeats() prepares SELECT COUNT(*) for this movie, reads the count from ResultSet, then subtracts it from totalSeats. The query deliberately counts every account's row. getSeatsJson() allocates one boolean per seat, runs SELECT seat_index for the movie, and marks each valid result true. It loops through the boolean array, converts each index back into a row letter and seat number, and builds JSON such as {"id":"A1","booked":false}. It also deliberately does not filter on account_id, so the live seat map is shared by everyone.

Database

Database is a small connection factory used by booking, catalogue, and authentication code. getConnection() reads DB_URL, DB_USER, and DB_PASSWORD from the process environment. If DB_URL is blank, it uses jdbc:mysql://localhost:3306/booking_app?createDatabaseIfNotExist=true&serverTimezone=UTC. If DB_USER is blank, it uses root. It refuses to connect when DB_PASSWORD is missing, then calls DriverManager.getConnection(url, user, password). The MySQL password is supplied at runtime; it is not a Java constant or a repository file.


AccountAuth.java - accounts and login sessions

AccountAuth is the authentication service. Its constructor receives three fixed identifiers: the account table, session table, and cookie name. MovieBooking supplies theatre_accounts, theatre_sessions, and theatre_session. This allows the same class design to be used in the separate flight repository with flight-specific table names.

initialize() creates theatre_accounts with an auto-increment ID, unique username, salt, hash, and creation timestamp. It then creates theatre_sessions with a token hash, account ID, expiry, creation timestamp, indexes, and a foreign key to the account. These tables are created at startup, before a visitor can submit the login form.

register() validates and normalizes input before writing anything. It generates a 16-byte random salt, encodes it for storage, and derives the password hash. It opens a database connection, disables auto-commit, inserts the account with a PreparedStatement, reads the new ID using getGeneratedKeys(), creates the initial login session, and commits. The account and session therefore succeed together. If SQL fails, it rolls back. Duplicate key error 1062 becomes an AuthException with HTTP 409.

login() normalizes the submitted username, fetches its saved salt and password hash using a parameterized SELECT, and derives a new hash from the submitted password and saved salt. MessageDigest.isEqual() compares the encoded hashes without a normal early-exit string comparison. If the account is missing or the hashes differ, it throws an authentication error and does not create a session. If they match, createLogin() inserts a new session.

createLogin() uses SecureRandom to create 32 bytes and Base64 URL-safe encoding to produce the opaque cookie value. It hashes that value with SHA-256 and inserts only the hash, account ID, and seven-day expiry into theatre_sessions. The raw token is returned to the HTTP handler only so it can set the cookie; it is not saved as a database value.

currentUser() asks readCookie() for the theatre_session cookie. readCookie() splits the Cookie header into name/value pairs and accepts only a URL-safe token of the expected length. currentUser() hashes the token, then joins theatre_sessions to theatre_accounts and requires expires_at to be later than the current database time. It returns a User containing the account ID and username, or null if the cookie is absent, malformed, expired, or unknown. Expired sessions no longer authenticate, but the code does not run a scheduled purge; old rows can remain until logout, account deletion, or database cleanup.

setLoginCookie() sets the raw session token as an HttpOnly, SameSite=Lax cookie with a seven-day Max-Age and Expires date. cookieHeader() adds Path=/ and adds Secure only when X-Forwarded-Proto says the request used HTTPS; this keeps local HTTP development usable while supporting a TLS-terminating proxy. logout() hashes and deletes the presented session token, then sends an expired cookie to the browser.

normalizeUsername() trims the text, enforces the username pattern, and lowercases it with Locale.ROOT so usernames are case-insensitive in application behavior. validatePassword() accepts 8 through 128 characters. hashPassword() uses PBKDF2WithHmacSHA256, 120,000 iterations, and a 256-bit result, then clears the PBEKeySpec's password copy. sha256() converts a byte digest to hexadecimal for the fixed-width database column.

User holds the authenticated account's integer ID and username. Login pairs a User with the newly generated raw session token for the response cookie. AuthException carries an HTTP status and a safe message for expected errors; unexpected SQLException is handled by the server as a database failure.


6. DATABASE TABLES

All four theatre tables are inside the booking_app MySQL database:

theatre_movies
One row per film. id is the primary key and matches the ID in the Java Movie object. title and show_time are display values. total_seats stores the capacity, 40 for each default film. The default list is defined in Java and inserted into this table at startup if absent. INSERT IGNORE means startup does not overwrite a row that is already there.

theatre_bookings
One row per reserved seat. movie_id points to theatre_movies.id. seat_index is a zero-based number from 0 to 39. customer_name is the name displayed on the reservation. account_id points to the signed-in account for new bookings; it is nullable so rows from before login was added can remain in the table. booked_at is added by MySQL when the row is inserted. The composite primary key (movie_id, seat_index) allows only one booking for a seat in a film. The foreign key on movie_id prevents a booking from referring to a missing movie. Old rows with a NULL account_id still count as booked.

theatre_accounts
One row per account. id is an auto-increment primary key. username is unique and limited to 30 characters. password_salt stores the random salt used for this account. password_hash stores the derived hash. created_at is filled by MySQL. Password text is not stored.

theatre_sessions
One row per browser login. token_hash is the primary key and contains the SHA-256 digest, not the browser's raw cookie token. account_id references theatre_accounts.id. expires_at is checked on every authenticated request. created_at is filled by MySQL. Indexes help look up a user's sessions and find expiring sessions. A foreign key links each session to an account and cascades session cleanup if an account is deleted.

Example booking relationship: an authenticated user has an ID in theatre_accounts. Booking the first seat of film 1 creates a theatre_bookings row with movie_id=1, seat_index=0, and that user's account_id. The seat map query checks movie_id and seat_index only; it does not filter on account_id.


7. HTTP API

GET /
Returns index.html. This is the landing page and the booking interface in one file.

POST /api/register
Creates an account, signs it in, and returns a session cookie.

POST /api/login
Checks credentials and returns a session cookie.

GET /api/session
Checks the current cookie and returns the signed-in username, or authenticated=false.

POST /api/logout
Deletes the current session and expires the cookie.

GET /api/movies
Requires login. Returns an array of objects with id, title, time, and available fields. Each available count is computed from the current database bookings.

GET /api/seats?movieId=1
Requires login. Returns a seats array. Each item has an id such as A1 and a booked boolean. The browser turns that boolean into an enabled or disabled seat button.

POST /api/book
Requires login. Accepts URL-encoded movieId, seat, and name fields. It returns a message and uses 200 for success, 400 for invalid movie/name/seat label, 409 for a seat already booked, and 500 for an unexpected database failure.


8. WHAT CONNECTS TO WHAT

1. The browser requests http://localhost:8080/.
2. MovieBooking reads index.html and sends it to the browser.
3. Browser JavaScript calls /api/session. For a signed-in user, the browser automatically sends its session cookie.
4. AccountAuth hashes the cookie token and checks theatre_sessions and theatre_accounts in MySQL.
5. After login, the page requests /api/movies and /api/seats. MovieBooking asks BookingSystem and Movie for the data; Movie reads booking rows with JDBC.
6. When the user books, the browser sends a POST to /api/book. Java validates the session and request, then Movie inserts the reservation into theatre_bookings.
7. The page reloads the seat map. A second account makes the same database query and receives the same booked-seat results.

Short architecture view:

Browser (HTML/CSS/JavaScript)
    | HTTP page requests and API calls; session cookie
    v
Java HttpServer (MovieBooking and AccountAuth)
    | JDBC queries and prepared statements
    v
MySQL booking_app database
    | theatre_movies, theatre_bookings, theatre_accounts, theatre_sessions


9. FRONTEND

index.html contains both screens. The first screen provides sign-in and account creation. After authentication, JavaScript hides the landing section and displays the booking section. The top bar shows the active username and a sign-out button.

The booking interface lists films on the left and draws the 5-by-8 seat map on the right. Available, selected, and taken seats have separate styles. The page uses JavaScript fetch() calls to the same Java server; no separate frontend server or JavaScript package manager is needed. CSS media queries adapt the layout for narrow screens. Form labels, button types, and aria-live status messages support keyboard and assistive-technology use.

The typography is DM Sans for general text, DM Mono for compact labels and seat codes, and Fraunces for film headings. Google Fonts provides the font files when the browser has an internet connection; fallback fonts are included in CSS.

Detailed browser JavaScript flow:

The state variables movies, selectedMovie, selectedSeat, and currentSeats hold only the data needed to draw the current page. They are temporary browser state, not the permanent reservation database. The DOM references movieList, seatGrid, bookButton, and message point to elements in index.html so event handlers can update them.

authMode is either login or register. setAuthMode() updates the active tab, heading, description, button text, and password autocomplete hint. The tab click handlers call it when the user switches between signing in and creating an account.

checkSession() runs once when the page loads. It requests GET /api/session. If Java reports a valid session, showBooking() hides the landing screen, displays the booking page, writes the username into the top bar and name field, and calls loadMovies(). If there is no session, the landing page remains visible.

The auth-form submit handler prevents a full browser page reload. It creates URLSearchParams for username and password, posts them to /api/login or /api/register, and reads the JSON response. While waiting it disables the submit button. On success, showBooking() opens the booking page. On an expected server error it displays the returned message; on a network error it shows a connection message. The password is sent to the same-origin Java server over the form POST and is never put into localStorage or the page URL.

The logout-button handler posts to /api/logout. The server removes the session. JavaScript then hides the booking section, shows the landing section, clears the password field, and resets the sign-in tab.

loadMovies() fetches /api/movies, saves the JSON array in movies, calls drawMovies(), and automatically selects the first film. drawMovies() maps each movie object to a button with its title, show time, and remaining seat count. The button's data-id links the visible card back to its Java object ID.

chooseMovie(id) changes selectedMovie, clears the currently selected seat and status message, redraws the film list, and requests /api/seats?movieId=id. It saves the returned seat array in currentSeats and calls drawSeats(). drawSeats() makes five rows and eight seat buttons per row. It marks database-booked seats disabled, marks the user's current selection, and disables Book a seat until both a seat and name are present.

The movie-list click handler uses event delegation: it finds the nearest .movie-option button even when the user clicks its nested title or poster. The seat-grid handler similarly finds a seat button and ignores disabled/taken seats. Typing in the name field recalculates whether the booking button should be enabled.

The booking-form submit handler sends movieId, seat label, and name to POST /api/book. When the API succeeds, it clears the selected seat, fetches the seat map and movie counts again, and displays the success message. When another account wins a race for that seat, it reloads the map and shows the server's error message. This refresh is what makes newly booked seats appear immediately without refreshing the whole browser page.

CSS variables near the top of the page define the paper, panel, ink, muted, line, and accent colors. Grid and flexbox place the movie list next to the seat map on wider screens. Media queries change the page to stacked panels on smaller screens. The CSS and JavaScript are embedded in index.html, so there is no frontend build step.


10. JAVA AND WEB CONCEPTS USED

Classes and objects: Movie contains a film and its seat operations. BookingSystem creates and finds Movie objects. MovieBooking starts the server and connects requests to those objects. AccountAuth handles user identity separately. This separation keeps web routing, movie data, and authentication from being one large method.
Encapsulation: fields such as Movie.id and AccountAuth.User.id are private or final and read through methods or package-local service objects. The caller asks Movie.bookSeat() to perform the operation rather than editing its seat data directly.
Arrays and loops: BookingSystem stores a fixed array of Movie objects. getSeatsJson() uses a boolean array indexed by seat number. Loops build API JSON and seat rows from these arrays.
HTTP server and routing: HttpServer accepts requests. The path and method determine whether the Java code serves HTML, authenticates a user, returns seat data, or inserts a booking. HTTP status codes tell the browser whether an action succeeded.
Concurrency: the fixed executor uses multiple worker threads. synchronized prevents overlapping calls to the same Movie object's booking or seat-read methods. It is process-local protection; the MySQL primary key is what still prevents a duplicate if two requests race at the database.
Database persistence: JDBC executes SQL using MySQL Connector/J. Each request opens a connection and uses try-with-resources to close connections, statements, and result sets. MySQL keeps the reservation after Java exits.
Relational keys: theatre_bookings.movie_id references theatre_movies.id. The composite primary key on movie_id and seat_index is a database rule that defines which seat is unique for one film.
Prepared statements: values such as account IDs, usernames, and seat numbers are bound with setInt()/setString(). SQL syntax stays separate from the user-supplied value.
Authentication: registration creates an account; login checks its password hash; a session cookie authenticates later API calls; logout revokes the session.
Password hashing: a random per-account salt and PBKDF2 make a database leak less useful than storing plain passwords. The random browser session token is also stored only as a hash in MySQL.
Exception handling: invalid forms use a controlled status and message. Duplicate-seat SQL error 1062 becomes HTTP 409. Other SQL errors reach the request-level handler and become HTTP 500.
Frontend events: event listeners handle login, logout, film cards, seat buttons, and booking forms. fetch() connects those events to the Java API without navigating to a new page.
Responsive web design: CSS grid, flexbox, fluid sizing, and breakpoints at 760px and 420px reorganize the page for tablets and phones.


11. RUNNING AND CONFIGURATION

Requirements: Java 11 or newer and a running MySQL server. From this project folder:

    ./run.sh

The script prompts for the MySQL password without echoing it. It starts the Maven Wrapper and runs MovieBooking. Open http://localhost:8080.

Optional environment variables:
DB_USER changes the MySQL username; default is root.
DB_PASSWORD supplies the MySQL password without an interactive prompt.
DB_URL changes the JDBC URL/database; default points to booking_app on localhost:3306.

Do not commit database passwords, application passwords, session tokens, or .env files. The repository's .gitignore excludes .env and Maven build output.


12. SOURCE FORMATTING AND SCOPE

The Java source uses four-space indentation, one class per clear responsibility where practical, descriptive method names, and try-with-resources for database objects. MovieBooking.java keeps the small theatre domain classes beside the server entry point; authentication is separated into AccountAuth.java. This is a deliberately small teaching project rather than a multi-module framework application.

The code demonstrates the full request-to-database path, but it is a classroom/demo system. It does not include email verification, password recovery, account administration, rate limiting, reservation cancellation, automatic expired-session cleanup, or a production connection pool.
